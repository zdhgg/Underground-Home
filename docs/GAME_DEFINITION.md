# 这个游戏到底做什么

日期：2026-10-17
输入：`docs/GAME_BRIEF.md`（基线 v0.5）、`AGENTS.md`、`docs/PHASES.md`、`docs/SPACE_DEPTH_REVIEW.md`、`docs/LAYER1_CONTENT_REVIEW.md`、`src/**`、`tests/**`
本文只回答一个问题：**《地下小家园》是什么游戏。** 不写功能清单，不写实施步骤。

---

## 0. 先说清楚为什么要这份文档

前几轮的做法是：试玩 → 发现"内容少 / 联系不大 / 动力不足" → 加一个系统（伙伴、遗物、引水、种植）。

每次都在回答"玩家下一步该做什么"，但从来没有回答"玩家**一直在**做什么"。

一个游戏如果没有"一直在做什么"，那么加多少内容都是**往一个没有底的桶里倒水**：倒进去就沉底，看起来有东西，但舀不起来。

所以先停一下，把桶底补上。

---

## 1. 设计基线其实已经回答了

`GAME_BRIEF.md` 第一句：

> 面向 7 岁儿童的 2D 横截面**地下家园建造与探索**游戏：地表风暴迫使小伙伴搬入旧避难所，玩家通过有限区域自由挖掘、修复设施、建立地下生态，让避难所**逐渐变成温暖、能运转的家园**。

核心体验第一条：

> **为什么挖**：为了找到能源、水源、开辟居住与生产空间；**禁止使用纯"挖 N 块土"充当主线目标**。

把这两句放在一起，原意非常清楚：

> **这是一个"把废墟变成家"的游戏。挖是手段，家是目的。**

不是"挖矿游戏"，不是"闯关游戏"，也不是"沙盒模拟器"。标题里的"家园"是主语，"地下"是舞台。

---

## 2. 但现在做出来的是另一个游戏

用代码事实对照一下（不是感受，是 `src/core/` 里的实际状态）：

| 基线说 | 现在实际是 | 差在哪 |
| --- | --- | --- |
| 自由挖掘、自主选择房间位置和层数 | 一条 8 步引导，一步接一步 | 从"沙盒"变成"教程" |
| 建立地下生态（水、食物、能源） | 水是一次性开关（`waterSupplied: boolean`），食物是"操作 3 次收一次" | 从"生态"变成"计数" |
| 伙伴使用设施、家园逐渐繁荣 | 伙伴住进床就不动了，没有需求、没有行为 | 从"生活"变成"装饰" |
| 建立"下一次向下拓展"的期待 | 只有两层；第二层做完就没有下一层 | 从"纵深"变成"两层" |
| 温和生存：缺电缺水**引导调整** | 没有"缺"的状态，所有资源都是"有 / 没有" | 从"生存"变成"解锁" |
| 第一夜 30–40 分钟，之后继续经营 | 20 分钟做完，之后静止 | 没有"之后" |

一句话：**设计写的是"经营"，实现做的是"清单"。**

清单的特点：每一项都有终点，做完就消失；经营的特点：每一项都连着下一项，永远有"接下来"。

---

## 3. 偏移是怎么发生的

不是执行错了，是**每次决策的坐标系不同**。

- 设计基线用"体验"做坐标：这一铲下去，孩子感觉到什么？
- 迭代用"缺口"做坐标：玩家说内容少，那就加内容。

用"缺口"做坐标，自然会得到"加一个系统"的答案。但系统之间没有共同的宿主，于是：

- 遗物和任务无关（挖到就完了）
- 伙伴和种植无关（住进来就不动了）
- 水和第二层无关（引上来就结束了）
- 第二层和第一层无关（除了那一次引水）

**每个系统都在自己的小圈子里闭环，彼此不咬合。** 所以玩家感受到的不是"内容少"，而是"这些内容跟我没关系"。

补丁打不出结构。要有一个**宿主**，让所有系统都挂在上面。

---

## 4. 重新定义

> **《地下小家园》是一个"为朋友造家"的游戏。**
>
> 你是一群小动物里最会挖洞的那一个。地表刮着风暴，大家躲进一个又黑又冷的旧避难所。你的工作是：听他们说想要什么，然后挖出空间、造出东西，让这个洞慢慢变成一个家。
>
> **伙伴想要什么 → 你去挖、去造 → 家变好 → 伙伴开心 → 又想要新的。**

三个关键词：

| 词 | 含义 | 不是什么 |
| --- | --- | --- |
| **家** | 玩家长期经营的对象，有状态、会变化、有记忆 | 不是"任务完成的背景板" |
| **朋友** | 需求的来源，也是成果的见证者 | 不是"住在床里的图标" |
| **造** | 挖和建是同一种动作的两个阶段：先掏空，再放进去 | 不是"挖矿"和"摆家具"两件事 |

### 核心动词是"照顾"，不是"挖"

这一句决定了所有系统的位置：

- 挖：**手段**（为了腾出空间）
- 建：**手段**（为了放东西）
- 探索：**手段**（为了拿到上面没有的东西）
- 伙伴：**目的**（他们的需求定义了"要挖什么、要建什么"）

如果把"挖"当核心动词，就会得到"挖矿游戏"，家园变成补给站。
如果把"建"当核心动词，就会得到"摆家具游戏"，挖掘变成清障。
只有把"照顾"当核心动词，挖和建才会被同一个理由驱动。

### 它解决三个反馈的方式

| 反馈 | 现在的处境 | 在"照顾"框架下 |
| --- | --- | --- |
| 内容少 | 任务做完就静止 | 愿望是规则生成的，永远有"下一件" |
| 联系不大 | 两层只有一次引水 | 愿望可以指向任何一层（"想要会发光的花"） |
| 动力不足 | 任务让我挖 | 朋友在等，我为他挖 |

注意：**同样的内容，框架不同，体验完全不同。** 现在这条任务链（找石头→修核心→建床→找水→引水→种菜）一条都不用删，换一个讲法就能成立。

## 5. 核心循环的四个时间尺度

一个好的儿童游戏，四个尺度都要成立。现在只有第一个。

| 尺度 | 玩家在做什么 | 现在 | 应该是什么 |
| --- | --- | --- | --- |
| **30 秒** | 点一下，有反应 | ✅ 挖一格、尘土、音效 | 保持 |
| **5 分钟** | 完成一件小事 | ⚠️ 只有"挖到石头"这种任务节点 | 满足一个愿望：挖空间 → 放床 → 伙伴入住 |
| **30 分钟** | 让家变一个样 | ❌ 没有 | 把"避难所"变成"有光有水的家" |
| **整章** | 从一层到下一层 | ❌ 没有（只有两层，且第二层没有"章"的内容） | 每一层是一个"家的新问题" |

**30 秒**已经有了，做得也不错（尘土、音效、高亮）。缺的是 5 分钟和 30 分钟的循环。

5 分钟循环的形状：

```
伙伴冒出一个愿望（图标气泡）
  → 玩家判断"这需要什么"（空间？材料？水？）
  → 挖 / 造 / 去下层取
  → 放好，伙伴自己走过去用
  → 气泡变成心，家多了一样东西
```

30 分钟循环的形状：

```
家的状态变化（更亮 / 更暖 / 更热闹 / 更大）
  → 新伙伴愿意来 / 新区域可以挖
  → 新的愿望类型出现
  → 玩家回头改造第一层（加房间、换布局）
```

**关键：30 分钟循环必须"回头"**。如果玩家一路向前不回头，第一层就会被丢掉——这正是现在发生的事。

## 6. 三种可能的定位

必须选一个当主体，另外两个当配角。三个都当主角，就是现在这个样子。

| | **A · 照顾型** | **B · 探索型** | **C · 建造型** |
| --- | --- | --- | --- |
| 一句话 | 我把废墟变成家 | 我家下面有更大的世界 | 我造一个属于自己的堡垒 |
| 核心幻想 | 被需要、有归属 | 好奇心、发现 | 创造、掌控 |
| 核心动词 | 照顾 | 发现 | 建造 |
| 挖掘的角色 | 手段 | **目的** | 前置 |
| 伙伴的角色 | **需求的来源** | 同伴 / 助手 | 居民 |
| 内容怎么长出来 | 愿望（规则生成） | 新地层（手工设计） | 新设施（手工设计） |
| 30 分钟循环 | 家变一个样 | 下到新一层 | 造出一片新区域 |
| 7 岁适配 | 高（情感直接） | 高（好奇心强） | 中（规划能力有限） |
| 与标题匹配 | 高 | 中 | 高 |
| 复用现有系统 | **最多**（伙伴/建/种/水都在） | 少（要大改地图与任务） | 中（要加大量设施） |
| 主要风险 | 变成"接任务-交任务" | 家园变装饰，标题失真 | 变成"摆家具"，没有为什么 |

### 推荐 A，理由不是"它最好"，是"它最省且最像这个项目"

1. **设计基线本来就写的 A**（"家园"是主语，"为什么挖"是第一条）。
2. **A 复用现有系统最多**：伙伴、睡眠舱、种植、引水、遗物全都能挂上去，不需要推翻地图和存档。
3. **A 的情感驱动对 7 岁最直接**："阿土怕黑"比"这一层有 3 个矿脉"更能让孩子动手。
4. **A 不排斥探索**：愿望可以指向下层（"想要会发光的花"），探索仍然是必需的，只是有了理由。
5. **B 的成本最高**：`SPACE_DEPTH_REVIEW.md` 已经算过，把地图放大到 3 屏、加材质分层、改存档，是一个中等规模重构；而且做完之后，如果家园仍然没有"一直在做什么"，问题会原样回来。
6. **C 的内容成本最高**：每种设施都要设计、绘制、写规则，而 7 岁孩子对"规划"的耐心有限，很容易变成"每个房间放一样东西"。

### A 的一个必要补充：不能只有"照顾"

纯照顾会变成"无限接任务"。所以 A 必须带两条"成长线"：

- **空间成长**：家从"一个洞"变成"三层堡垒"（玩家看得见的规模变化）
- **能力成长**：从"只能挖土"到"能挖岩石、能挖更深"（玩家感觉得到的手变强）

照顾提供"为什么"，成长提供"然后呢"。两条腿走路。

## 7. 选 A 之后，第一夜重新长什么样

**内容一条都不用删，换框架。**

现在的框架是"任务清单"：`找到发光的能源石 1/4`。
新的框架是"家的故事"：每一步都是**家里的一个问题**，解决了就有下一个问题。

| # | 家里的问题（谁在说） | 玩家做什么 | 家的变化 |
| --- | --- | --- | --- |
| 1 | "这里好黑，我有点怕。"（阿土） | 挖开左边的泥土，找到能源石，修好核心 | 灯一盏一盏亮起来，大厅暖了 |
| 2 | "亮了！可是……我们睡哪儿？"（阿土） | 挖出一块空地，放下睡眠舱 | 两位伙伴钻进去，冒出 Zzz |
| 3 | "床好舒服。可是没有水，没法做饭。"（阿土） | 顺着裂纹往下挖，找到泉水 | 泉水露出来，有水声 |
| 4 | "还有两位朋友说，有水才肯来。"（阿土） | 把水引上来，再安一张床 | 两位新朋友住进来 |
| 5 | "我想吃点新鲜的。"（新朋友） | 摆种植槽，种出第一份菜 | 收成，大家围在一起吃饭 |
| 6 | "家越来越像家了。"（阿土） | 自由建设 | 镜头拉远，全景 |

**和现在的区别只在"谁在说话"和"为什么"**：

- 现在：`找到发光的能源石` + `点一点泛蓝光的泥土`——是系统在给指令。
- 新的：`这里好黑，我有点怕` + `挖开左边泛蓝光的泥土，找一找能源石`——是朋友在求助。

7 岁孩子对"朋友怕黑"的反应，比"任务 1/4"强得多。这是**零成本的改动**（只改文案和顺序），但它是整个框架的试金石：如果换了讲法孩子仍然无感，那说明问题不在框架，在别处。

### 每一步都要有"家的变化"

现在的问题是有几步"做完了但家没变"：修核心有变化（灯亮），建床有变化（伙伴入住），但"收集能源石"和"引水"的变化很弱。

新框架要求每一步结束时，**画面里必须有一样东西变了**：多一盏灯、多一个人、多一间房、多一棵菜。这是"照顾"的即时回报。

## 8. 内容结构：层 = 章

如果接受 A，那么"层"就不是"地图的一块"，而是**"一个家的新问题"**。

| 层 | 主题 | 家里的问题 | 新增的东西 | 章末的完成感 |
| --- | --- | --- | --- | --- |
| 第 1 层 · 暖窝层 | 居住 | 黑、冷、没地方睡 | 能源、睡眠舱、伙伴 | 灯全亮，两位伙伴睡着 |
| 第 2 层 · 泉水层 | 生产 | 没水、没吃的、新朋友不肯来 | 水、种植、新伙伴 | 第一顿饭，四个人围着吃 |
| 第 3 层 · ？（未来） | 未知 | 家够大了，但只能靠一盏灯 | 新材料、新工具、更深的探索 | 三层全景，灯火通明 |

每一层的结构是一样的：

```
到达时是黑的、空的、有问题的
  → 解决 3–5 个"家里的问题"
  → 这一层亮起来、有人住、有东西产出
  → 发现下一层的入口（钩子）
```

**"愿望"是这一层内容的生成器**：每个伙伴 2–3 个愿望，愿望的内容由"这一层的主题"决定。第二层的伙伴会想要"会发光的花""能看水的窗"，第三层的伙伴会想要"能听见上面声音的房间"。

这样内容不需要手工写死每一条，只需要定"这一层能出什么愿望"。

### 愿望必须有尽头

对 7 岁孩子，"永远有新愿望"= "永远做不完"= 压力。

所以每层结尾要有一个**明确的完成态**：灯全亮、所有伙伴都有床、第一顿饭吃完、镜头拉远、阿土说"这是我们的家了"。

然后才出现下一层的入口。**"完成"是下一章的开始，不是内容的耗尽。**

## 9. 这个定义排除了什么

明确不做，比明确做什么更重要。

| 不做 | 原因 |
| --- | --- |
| 不做"挖矿经济"（矿石换钱、买装备） | 会把核心动词从"照顾"变成"刷资源"，且 7 岁不需要经济系统 |
| 不做"生存压力"（饥饿条、死亡、倒计时） | 违反基线的"温和生存"；照顾不等于惩罚 |
| 不做"随机地图" | 基线的"固定小地图 + 手写蓝图"是有意的：任务引导要可靠，孩子不能迷路 |
| 不做"战斗 / 怪物" | AGENTS.md 明确暂缓 |
| 不做"多结局 / 分支叙事" | 7 岁不需要选择后果，需要"我做了一件好事"的确定感 |
| 不做"无限愿望" | 每层必须有完成态，否则变成永远做不完的清单 |
| 不把"层"做成独立地图 | 见 `SPACE_DEPTH_REVIEW.md`：切层会丢掉"一眼看见整个家"的最大优势 |

---

## 10. 下一步：先验证定义，再动系统

不要一上来就做愿望系统。先用**最小改动**验证"这个定义对不对"：

**第一步（只改文案和顺序，不动规则）**
把第一夜的 6 步改成"家里的问题"的讲法（见第 7 节），看孩子是否会主动问"阿土还想要什么"。

**第二步（如果第一步成立）**
做"愿望"的最小版本：每位伙伴一个愿望、一个气泡、一个满足判定、一件小回报。不做愿望树，不做无限生成。

**第三步（如果第二步成立）**
把愿望接到第二层的材料上（"想要会发光的花"），验证"愿望能不能驱动向下"。

三步都成立之后，才值得动地图、加层、改存档。

---

## 一句话

**这个游戏不是"挖一个地下堡垒"，是"和一群朋友一起，把一个洞变成家"。**

挖是手段，建是手段，探索是手段。**"他们还需要什么"才是目的。**

所有系统都应该回答同一个问题：**它让"家"发生了什么变化？** 回答不了的系统，就不该加。
